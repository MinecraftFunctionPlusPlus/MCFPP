# MCFPP 异常效果系统设计草案

日期：2026-10-06。状态：设计提案，未实现。本文的 `error`、`throw`、`catch`、`finally`、`throws` 均为拟议语法，不能直接交给当前编译器执行。

2026-10-07 更新：用户明确模拟调用栈只是临时策略，并要求以全局跨 tick API 与零成本抽象为目标。物理调用、异常传播和暂停后端以 [无栈回溯依赖的效果与任务设计](stackless-effects-and-tasks-design.md) 为准；本文第 8、9 节的统一帧协议不再是推荐的最终架构。

Java 对比与逐文件 Minecraft 命令示例见 [异常效果系统命令展开](exception-effects-examples.md)。

## 1. 推荐方案与成功标准

采用**可推导、静态检查的类型化异常效果**：开发者通过 `throw / try / catch` 使用异常，编译器在函数签名中追踪可能逃逸的错误集合，并将异常降为明确的控制流和帧内状态。

异常是不可恢复的控制效果：`throw` 放弃当前位置后续的计算，转到最近的匹配处理器；若处理器正常完成，则继续执行整个 `try` 之后的语句。不回到抛出点。首版不引入 `perform`、`resume`、continuation 或通用代数效果处理器。

| 目标 | 验收条件 |
| --- | --- |
| 学习成本低 | 入门只需错误声明、抛出、捕获；普通调用无需 `?` 或额外包装 |
| 开发者友好 | 自动推导传播集合；未处理错误给出类型、来源路径及可操作的修改建议 |
| 可检查 | 每个语言入口的逃逸错误集合必须为空；库边界携带效果契约 |
| 高效 | 没有异常相关操作且调用目标均不会抛出的函数，不增加异常槽、检查或处理器登记命令 |
| 语义稳定 | 成功值只在正常边可读；错误边保留抛出前的状态修改；递归不污染其他帧 |
| 可扩展 | 内存效果、异常效果分开建模，为将来的高阶效果多态预留位置 |

“不会抛出”不等于“纯函数”，也不等于“会终止”。循环、世界修改、原始命令仍有各自的语义。

## 3. 三个概念即可入门

### 3.1 声明与抛出

```mcfpp
error InvalidPrice(price as int);
error InsufficientFunds(balance as int, required as int);

func debit(balance as int, price as int) -> int {
    if (price < 0) {
        throw InvalidPrice(price);
    }
    if (balance < price) {
        throw InsufficientFunds(balance, price);
    }
    return balance - price;
}
```

推导得到 `debit: (int, int) -> int throws(InvalidPrice, InsufficientFunds)`。返回类型仍是 `int`。错误集合属于函数调用契约，不进入普通值的返回类型。

`error E(fields...)` 是专用名义数据声明：自动生成构造器和只读字段，隐式属于内建错误根 `Error`。首版错误类型 final，不支持用户错误继承、泛型错误或带效果的错误构造器。无载荷错误可以写 `error NotFound;`，用 `NotFound()` 构造。

首版字段限于已有后端可以安全编码的值；不允许 `type` 等编译器专用载荷。错误快照拥有独立数据，不保存指向即将销毁的被调用帧的视图。不可编码字段在声明或实例化处给出诊断。

### 3.2 捕获与继续

```mcfpp
func purchase(balance as int, price as int) -> int {
    try {
        return debit(balance, price);
    } catch (e as InvalidPrice) {
        /say Invalid price
    } catch (e as InsufficientFunds) {
        /say Not enough coins
    }
    return balance;
}
```

`purchase` 不再向外抛出这两种错误。原始 `/say` 仍然是内存分析的外部状态屏障，因此不能把 `purchase` 标为内存纯函数。

`catch` 按源码顺序匹配第一个适用分支。可以使用 `catch (e as (A | B))` 捕获多个类型，使用 `catch (e as Error)` 捕获任意语言错误。联合捕获中的 `e` 只暴露共同可用接口，类型专有字段需要进一步收窄。

错误只能通过 `error` 声明产生。普通模板、字符串、`any` 或任意 NBT 不能通过 `as Error` 获得可抛出身份。错误封装的类型标签不改变普通 `any/object` 的无标签载荷设计。

### 3.3 自动传播

```mcfpp
func checkout(balance as int, price as int) -> int {
    return debit(balance, price);
}
```

无需逐层写 `throws`、`try` 或 `?`。`checkout` 自动继承未处理的两种错误。错误可以经过多层调用，最终必须在入口之前被捕获。

## 4. 可选的效果契约

```mcfpp
func documentedDebit(balance as int, price as int) -> int
    throws(InvalidPrice, InsufficientFunds) {
    return debit(balance, price);
}

func safeDebit(balance as int, price as int) -> int throws() {
    // 必须处理所有可能逃逸的错误
    return purchase(balance, price);
}
```

`throws(...)` 是**上界**：推导出的逃逸集合必须是声明集合的子集。`throws()` 表示不向调用者抛出；函数内部仍可抛出并自行处理。`throws(Error)` 表示任何语言错误，是已知但宽泛的契约，不等同于未解析效果。

本地未标注函数自动推导。导出函数也允许自动推导，导出时将结果固定为库契约；发布后增加可逃逸类型属于契约变化。建议稳定公共 API 显式声明，默认不强制每个函数手写。

有显式声明时，独立编译调用者按声明上界检查，不能依赖当前函数体恰巧少抛一种错误。只有取得函数体并验证等价的优化阶段才可以利用更精确的实现摘要。消除检查时仍须遵守既定 ABI。

重载选择继续依据参数与既有类型规则，不根据调用方是否有某个 `catch` 来选择重载。同参数签名、只在 `throws` 上不同的两个函数视为重复声明。覆盖方法的逃逸集合不能扩大父签名上界；通过父类型调用时使用父契约。

语法中的类型名由编译器静态解析，不是将 `type` 值放入普通变量或运行时参数，因此与现行 `type` 声明限制兼容。

### 4.1 语法范围与兼容性

以下 EBNF 省略现有换行与 separator 规则，用于约束新增语法范围：

```text
errorDeclaration = "error" Identifier [ "(" errorFields ")" ] separator
errorFields      = [ Identifier "as" type { "," Identifier "as" type } ]
throwsClause     = "throws" "(" [ type { "," type } ] ")"
throwStatement   = "throw" expression
tryStatement     = "try" curlBlock
                   ( catchClause { catchClause } [ finallyClause ]
                   | finallyClause )
catchClause      = "catch" "(" Identifier "as" type ")" curlBlock
finallyClause    = "finally" curlBlock
```

`throwsClause` 接在返回类型之后、函数体或原生绑定之前；无显式返回类型时接在参数列表之后。catch/throws 中只允许错误类型、错误联合或根 `Error`，其他普通类型给语义诊断。首版只提供语句级 try、带值 throw，不增加 try 表达式、裸 throw 或捕获条件过滤。

**`error` 必须是声明位置的上下文关键字**：当前标准库 `src/main/mcfpp/lang/sys.mcfpp` 已有 `func error(string)`，不能新增一个排除 Identifier 的全局 ERROR token 导致该函数失效。`throws` 同样只在签名尾部识别，名字位置仍允许旧用法。`throw/catch/finally` 作为新保留字随异常特性的语言版本引入；已有用户声明若占用这些名字，必须给明确的重命名迁移诊断，不能静默改变解析结果。当前标准库搜索只发现 `error` 名称冲突，但发布前仍需扫描用户测试与语言支持仓库。词法改动必须同步普通、成员和原生声明的解析测试。

## 5. 效果模型与推导

建议内部模型为乘积，以下为示意结构，不是已新增的 Kotlin API：

```text
FunctionEffects {
    memory: ExistingMemoryEffect
    raises: Closed(Set<ErrorTypeId>) | AnyError | Unresolved
}
```

`Closed({})` 表示无逃逸异常；集合并是 join；`AnyError` 是所有合法错误的上界；`Unresolved` 表示分析或 ABI 契约尚未确定，不能进入代码生成。捕获 `Error` 可以消除 `AnyError`，不能修复 `Unresolved`。

每个函数的错误集合按调用图最小不动点求解。首版名义错误集合有限，递归传播只增加类型；不需要仿照内存写路径进行无限路径扩展。采用 SCC 工作队列并保存一个代表性来源链，避免为每条递归路径重复保存诊断数据。

基本规则：

```text
R(throw E(value)) = R(value) ∪ {E}
R(call f(args))  = R(args 按求值顺序) ∪ Contract(f)
R(sequence)     = 所有可达节点的逃逸集合之并
R(try B catch H1 ... Hn)
                = (R(B) \ CoveredTypes)
                  ∪ 所有可达处理器自身的 R(Hi)
R(try/catch finally F)
                = R(try/catch) ∪ R(F)   // 保守上界
```

上述是摘要规则；具体 lowering 必须依据正常边、异常边和不可达路径计算，不能把已退出后的语句仍计入效果。静态证明死分支可以移除其效果；未知运行时条件取并集。首版无需依赖复杂的谓词证明获得可接受的签名。

同一组 `catch` 只处理 `try` 主体抛出的错误。处理器自身抛出或 `throw e` 重抛的错误传给外层，不交给自己的兄弟 `catch`。处理器入口将 `e` 的类型集合收窄为匹配集合；重抛保留该集合和载荷，避免无端扩大为 `Error`。

已被前序捕获完全覆盖的分支给警告；无法从主体到达的捕获也给提示。未知外部契约不能用一个空集合代替。

## 6. 控制流、状态修改与 finally

表达式、接收者、下标和实参按现有求值顺序执行。一旦某次求值抛出，停止求值其余部分。例如 `combine(first(), second())` 中 `first()` 抛出时，`second()` 和 `combine` 都不执行。

抛出前已执行的全局、字段、世界修改仍然可见；不自动回滚。现有 `static` 参数以调用结束写回的语义为基础：异常结束也写回抛出前的最终状态。普通按值参数副本不写回。参数准备未完成、目标尚未进入时，不执行该目标的写回，但此前实参计算的副作用保留。

```mcfpp
error ProcessingFailed;

func example() {
    try {
        throw ProcessingFailed();
    } catch (e as ProcessingFailed) {
        /say Handled
    } finally {
        /say Cleanup
    }
}
```

`finally` 可跟在 `try/catch` 后，也可用于只有 `try/finally` 的结构。退出其作用域的正常完成、`return`、异常、离开该作用域的 `break/continue` 都执行一次；仍在该作用域内部跳转的循环不触发提前清理。嵌套结构从内到外清理。

正常返回先求值并保存返回值，再执行 `finally`；清理对来源变量的修改不改变已捕获的返回快照。`finally` 正常结束后恢复原退出原因。

首版禁止 `finally` 中跳出清理体的 `return/break/continue`，避免隐式吞掉错误；清理体内自有循环的局部跳转允许。清理可以抛出新错误：新错误取代待处理的返回或错误，并继续执行尚未执行的外层清理。首版不自动建立 suppressed 异常链，原错误可在可选调试记录中保留。

引擎命令链超限、服务器停止、编译器错误不是语言异常，无法保证由 `finally` 收尾。此边界属于执行环境限制，不计入可捕获错误集合。

## 7. IR 与流分析

建议将可能抛出的调用从普通指令变为有两个出口的 `Invoke` 终结符；不会抛出的调用继续使用现有 `Instruction.Call`。

```text
Invoke(target, capturedArguments,
       normalBlock, exceptionalDispatchBlock)
Raise(errorSnapshot)
```

处理器作用域在 lowering 中静态维护，异常出口连接到该位置最近的匹配分派；跨函数错误仍由各调用者传播。源码上调用者建立的 `try` 可以捕获被调用者的错误，首版不提供可携带出作用域的一等处理器。

必须同步扩展 `FlowAnalysis`、`ReturnTypeAnalysis`、效果分析与后端，不能只增加命令标志：

- 正常出口才能定义调用结果，异常出口没有可读成功值。
- 异常出口包含调用前以及被调用者抛出前的实际/保守修改；已捕获异常不撤销 `Writes`。
- 现有返回与写回摘要主要面向正常出口。首版异常边对受影响位置保守失效，不把正常返回的类型证明用于异常边；未知内存效果仍使用屏障。后续可以分别求解正常/异常写回摘要。
- `throw` 后同一顺序路径不可达；所有正常路径返回值与异常路径应分别验证。
- 返回值、错误载荷、待执行清理的退出原因使用不同槽。`finally` 中的调用不能覆盖 pending 错误。

例如在 `try` 外声明且仅在成功调用后初始化的变量，不能在异常路径上被认定为已初始化。只有所有到达合流点的路径都初始化，之后才可读取。

## 8. Minecraft 运行时 ABI

本节保留为早期帧后端方案；最新方案将逻辑异常出口与物理存储解耦，按场景选择直接分支、Outcome ABI 或兼容帧适配器，见 [新版第 7、8 节](stackless-effects-and-tasks-design.md)。

第一版采用**帧内状态 + 异常载荷**，不建立全局动态处理器搜索栈，不把 Minecraft 函数返回数值当作语言异常或普通返回值的唯一通道。

只有按契约可能向外抛出的函数需要外部异常出口。概念布局：

```text
calleeFrame.$exit = {
    failed: 0b,
    error: { type: "canonical error identity", payload: {...} }
}
```

成功入口初始化 `failed:0b`，无需初始化 `error` 字段。`throw` 捕获独立载荷、写入规范身份并设置 `failed:1b`，通过异常出口完成清理。错误身份使用无歧义的稳定规范字符串，以已有 `TypeId` 的声明身份为基础；示意字符串不是允许名称的正式编码规范。

首版捕获使用 NBT 常量类型谓词匹配，与库编译顺序无关。可选的整数类型编号属于后续链接优化，必须重定位所有库函数与捕获分派；禁止各库独立分配编号后直接拼接。

可能抛出调用的收尾协议：

1. 按顺序捕获接收者和实参，保存跨调用活跃值，建立被调用帧。
2. 执行目标函数；目标的语言异常出口先执行所属作用域清理。
3. 被调用帧尚在时，将错误状态及失败载荷转移到调用者专属调用出口槽。正常返回值只在成功时复制。不要读取上一次遗留的返回槽。
4. 无论成功失败，保存 `static` 形参最终值，退栈，恢复调用者寄存器，完成写回。
5. 恢复完毕后分支：成功进入正常续块；失败进入最近处理器或当前函数的异常收尾块。

被调用者退出自己的函数，不可以直接删除由调用者管理的调用帧。复用 `frameExits` 时要明确收尾所有权，防止异常出口重复退栈或漏退栈。

每次调用有独立出口槽；递归、嵌套捕获、清理内调用不能复用同一个全局错误变量。只在真实函数帧入口初始化自己的外部出口，不能在共享该帧的基本块或辅助函数入口重置失败状态。

函数在内部使用 `try/catch` 但对外 `throws()` 时，内部仍可能有异常分派命令；它的调用者不需要额外检查。不可将“外部集合为空”宣传成函数体内异常实现完全无开销。

## 9. 目标版本与性能策略

后端按已有能力表选择控制流方案，不按一个简单版本阈值假设所有 `return` 形式都可用。

- 支持对应命令的目标：用基本块尾部 `return` / `return run function` 提前离开辅助块；调用边界仍通过帧内出口恢复和分派。
- 不支持相应形式的目标：将可能抛出的调用切在块尾，生成受状态保护的正常/异常续块。当前旧目标分支栈可以作为参考，但要验证回边和嵌套不会重复进入另一出口。
- 两种后端共用异常 ABI，保证库与调用者对状态及载荷的解释一致。

性能承诺只涉及可验证的结构；首版不承诺“所有成功路径零开销”：

| 场景 | 相对无异常实现的预期开销 |
| --- | --- |
| 无异常操作、调用均不抛出 | 异常系统新增命令数为 0 |
| 可能抛出函数成功返回 | 初始化出口、传递状态、选择续块；正常路径不构造/复制错误载荷 |
| 本地捕获 | 只在错误边做类型分派；静态已知错误可直接跳转 |
| 跨函数抛出 | 载荷转移与逐调用边传播，随经过的调用边及载荷大小增长 |
| 包含 finally | 所有穿过清理作用域的出口承担清理代码成本 |

优化顺序：可达性剪枝 → 错误集合收窄 → 本地直接异常边 → 出口槽活跃性复用 → 可选错误载荷所有权转移。首版先复制保证正确；以后才能在证明无别名时减少复制。

暂不按每个处理器环境无限特化函数，不预先字符串化错误，不默认构造完整运行时调用栈。发布构建保留错误类型与载荷；调试构建可按需保存源码位置和调用边信息。

## 10. 多实体执行与调度边界

语言层多实体 `execute` 采用**遇错停止本组后续迭代**：前面实体已经产生的修改保留，失败实体之后的迭代不再执行，异常交给该 `execute` 外的匹配处理器。

```mcfpp
try {
    execute(as = @a) {
        work();
    }
} catch (e as WorkFailed) {
    // 此处回到 execute 外层上下文
}
```

`work`、`WorkFailed` 是示意的业务函数和错误。若开发者需要每个实体失败后继续，应把 `try/catch` 放入 `execute` 主体内，此时处理器使用对应实体上下文。

为实现这个语义，可能逃逸异常的多上下文执行必须由编译器生成有保护的逐上下文主体或显式迭代，后续上下文检查组内失败状态并跳过。不能只对原始 `execute as @a run function ...` 使用 `return` 就声称整个组会停止。实体迭代次序沿用目标选择器/执行语义，不额外承诺排序；处理器切换上下文必须由 lowering 明确表达。

组内失败状态由本次 `execute` 所属调用帧持有，内层实体调用拥有独立被调用帧。没有逃逸异常的 `execute` 可保持现有输出形态。

load、tick、事件函数、顶层执行及供原始 `/function` 调用的外部入口，都要求 `raises = Closed({})`。对需要从 Minecraft 命令触发的可抛出业务函数，生成或要求一个明确捕获并报告错误的包装入口。错误不能悄悄落入默认吞错处理器。

跨 tick 调度不继承提交时的处理器。被调度主体是新入口，必须自行处理；若将来要将失败作为数据返给调度方，可在任务记录中显式保存结果。

## 11. 原始命令、原生函数与宿主错误

普通 Minecraft 命令未成功，不自动等同于 MCFPP 异常。选择器为空、条件未命中、命令返回数值为 0 都有正常用途；命令 success 与语言异常属于不同通道。

需要强制成功时，提供明确的 checked 标准库操作，把指定失败条件转成具体错误，例如 `CommandFailed`。该操作的具体命令捕获语法另行设计；首版不在字符串内部解析和插入隐式 `throw`。

保留 `try ... store(identifier)` 为独立旧语法，不偷偷将它升级为 `catch`。新增 `try` 形式用后续 `store`、`catch`、`finally` 区分；若旧实现尚未完整，需要独立验证其行为。

同理，首版不自动改变现有 `/`、集合索引等操作的运行时错误语义。可以新增 `checkedDivide`、checked 集合操作并声明对应错误。是否在未来语言版本统一加入隐式异常，是单独的兼容性决策。

原生函数契约包含两个独立部分：已有内存效果，以及 `raises` 和异常 ABI。无外部写入不推出不会抛出。缺少新的异常契约时，在进入异常检查路径前必须完成适配；不能把未确认原生实现当作已证明 `throws()`。

现有已知旧 ABI 的函数体不能产生新语言异常，可通过经过审核的 legacy 适配标记为不抛出；未知/不匹配 ABI 的库或原生目标必须重编译、提供适配或报错。首阶段不全局改写所有旧代码，应明确支持范围并阻止在新异常路径中静默回退。

编译器 Kotlin/Java 抛出的宿主异常不跨到生成的数据包；编译器诊断也不可被用户 `catch` 捕获。编译期函数中的语言异常则由编译期解释器处理，同样检查效果；无法执行的编译期路径必须报诊断，不生成伪造的运行时成功结果。

## 12. 库、函数类型与将来的效果多态

库元数据至少保存：错误规范身份及字段布局、导出逃逸集合/上界、异常 ABI 版本。导入时核验身份及布局，不使用本次进程临时 `SymbolId` 作为跨库错误标识。需升级 MCFL 并以生产者/消费者独立进程和反序导入验证。

异常集合是函数签名的一部分，普通值 `TypeId` 不混入调用者处理器环境。将来函数值的兼容规则是：实参函数可能抛出的集合必须落在形参允许的上界内；泛型类型特化与效果特化不能互相假装。

对于高阶函数，最终应支持效果变量，例如以下**类型关系示意，不是首版表面语法**：

```text
map: (List<T>, callback: T -> U ! ε) -> List<U> ! ε
```

调用 `map` 时由回调效果确定 `ε`，避免“只接受不抛出回调”或“所有回调都扩大为 Error”。首版先支持已覆盖的直接函数调用；一等函数/回调进入范围时，闭合的效果契约必须先完整传递，再引入效果变量推导。

错误转为普通 `Result<T,E>` 适合批量收集失败、保存任务结果和跨 tick 数据传递，但不作为首版调用的必备包装。待普通 Result 类型及高阶语法确定后，再提供捕获到 Result 和从 Result 抛出的明确转换。

通用可恢复效果需要捕获/恢复计算和新的成本模型，另立提案；本设计不声称已提供完整 algebraic effects。

## 13. 诊断与编辑器体验

优先给出“什么错误从哪里逃到哪里”，再提供效果术语。示意诊断：

```text
入口 onPurchase 有 1 种未处理错误：InsufficientFunds
  onPurchase -> checkout -> debit
  debit 的 throw 位于 shop.mcfpp:18

建议：在 onPurchase 调用附近添加 catch (e as InsufficientFunds)。
```

显式 `throws()` 的违约在函数声明处给错误，并关联导致逃逸的调用/抛出点。普通函数可以自动传播；入口不能通过添加 `throws(...)` 修复，必须捕获或改为由安全包装入口调用。

编辑器 hover 显示推导后的 `throws(...)`，补全列出尚未捕获的错误。快速修复提供捕获骨架，允许普通函数增加显式契约；不要自动插入空捕获或静默默认值。不可达捕获提示默认不阻止编译。

首版诊断可先由编译器提供；语言支持仓库后续再接 hover 与修复，本轮不修改它。

| B：单调用纵向路径 | 普通函数 `throw/try/catch`、Invoke、双出口、帧内 ABI、单目标后端 | 成功与错误边、实参短路、帧平衡、static 写回、嵌套/递归通过端到端测试 |
| C：结构化退出 | finally、return/break/continue、循环、多实体 execute | 每种穿越退出恰好清理一次；旧目标续块与上下文切换正确 |

| E：优化与扩展 | 命令数回归、载荷复制优化、效果多态/Result 独立提案 | 正确性基线不变；有生成命令与服务器实测数据支持 |

B 的实验版本必须明确拒绝尚未支持的结构；达到 C、D 后才作为默认语言异常体系发布。先从当前 `PrimitiveCompiler` 支持的普通函数闭环入手，避免在旧 visitor 与新 IR 中各实现一套不同语义。

## 16. 资料依据与选择理由

[Koka 官方 Effect Typing](https://koka-lang.github.io/koka/doc/book.html) 展示将参数、结果与效果分开，并推导函数效果。MCFPP 借鉴这一分离与推导原则，表面语法和类型化错误集合为本提案的选择。

[Effekt 官方 Effect Handlers](https://effekt-lang.org/docs/concepts/effect-handlers) 展示错误效果被处理后从外部效果中消除，以及恢复执行的扩展。本提案只采用不可恢复异常这部分，降低语言与 Minecraft 后端的实现成本。

[Effekt 官方 Effect Safety](https://effekt-lang.org/docs/concepts/effect-safety) 说明调用上下文对效果承担要求。MCFPP 的入口零逃逸规则借鉴静态效果检查目标；本文的调用者最近匹配 catch、帧内 ABI 和 execute 规则是 MCFPP 自己的设计，不能直接当成 Effekt 原有语义。

[Minecraft 1.20.3 官方发布说明](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-20-3) 记录了 `return run` 的重新引入及结果/成功状态的变化。因此后端必须依据具体命令能力处理版本差异，并将语言异常与 Minecraft 命令成功分开。

主要取舍：以熟悉的异常语法隐藏效果集合的手工管理；用可检查契约保证边界；以显式双出口和帧状态适应 Minecraft，接受可能失败调用成功路径上的小额检查成本，避免引入运行时 continuation 与动态处理器搜索。

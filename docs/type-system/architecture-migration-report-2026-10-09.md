# MCFPP 类型系统迁移技术报告

日期：2026-10-09。当前代码提交：`fcfbdef`。

本报告比较迁移前的设计与当前结构。迁移分多次提交完成，部分基础模块在最后一次提交前已经建立。

MCFPP 将自己的语言编译为 Minecraft 数据包命令。本次迁移保留主要目录，重新划分编译器内部职责。核心变化是分开管理声明类型、已知值、数据位置和副作用。

## 1. 项目结构的变化

下表中的路径以 `src/main/kotlin/top/mcfpp/` 为起点。

| 部分 | 之前的结构 | 现在的结构 |
| --- | --- | --- |
| 值与变量 | `core/lang/` 中的 `ConcreteVar`、`MCFPPValue` 和多种 Concrete 子类区分已知值与动态值。变量还保存多种状态标志。 | `analysis/ValueModel.kt` 和 `CompilerValue.kt` 统一描述值与状态。原有 `Var` 和领域类型仍作为接口接入这些信息。 |
| 表达式与声明分析 | 部分路径通过执行表达式来探测声明类型。常量表达式还有独立访问器。 | `DeclarationBinding.kt` 查询声明和函数签名，不执行用户初始化。表达式访问器、`TypedIR.kt` 和原生接口共享值与存储规则。 |
| 存储与调用 | 不同变量类分别处理记分板、NBT、入栈、取值和动态化。 | `analysis/StorageAccess.kt` 统一读取、写入、复制和运行时存储。它记录求值时的下标、调用帧和数据来源。 |
| 原生接口 | 宿主调用存在包装器和历史签名分支。 | `mni/NativeCallContext.kt` 提供统一调用上下文。原生方法读取参数和接收者，并通过统一接口发布结果。 |
| 副作用 | 状态标志和各调用路径分别维护部分信息。 | `analysis/EffectAnalysis.kt` 描述调用会读取或修改哪些位置。存储层据此撤销过期信息。 |
| 库文件 | 字段元数据直接保存 `Var` 对象，容易携带与原编译过程有关的状态。 | `io/info/VarInfo.kt` 保存字段描述，`TypeDescriptorSerializer.kt` 保存类型描述。导入时重新建立声明环境。 |
| 命令后端 | 类型类承担较多存储和运算职责。 | `backend/`、`command/` 通过统一值和位置接口生成命令，并保留目标版本的实现差异。 |

这里的“原生接口”是编译器调用 Java/Kotlin 方法的接口，不是操作系统的原生代码接口。IR 是中间表示，用于记录操作和控制流。NBT 是 Minecraft 使用的数据格式。副作用分析记录调用对外部数据的读取或修改。

## 2. 新值模型如何工作

新模型分别回答四个问题：

- `Symbol`：变量声明了什么类型，允许怎样修改？
- `CompilerValue`：编译器是否拥有完整、不可变的值快照？
- `Place` 和 `Location`：数据属于哪个位置，访问时捕获了什么下标或调用帧？
- `ValueFacts`：编译器目前知道什么类型、值和初始化状态？

例如，一个来自运行时输入的整数具有明确的 `int` 类型，但编译器不知道它的数值。新模型可以同时表示这两条信息，不需要用另一种变量子类代表“未知整数”。

初始化状态也独立保存。未赋值、某些分支已赋值、已赋值和错误具有不同含义。`null` 是一个实际值，不代表未赋值。

递归数据模板使用已绑定的类型描述读取字段。例如，`Node.next` 仍可以指向 `Node`。编译器沿实际访问路径处理字段，不预先无限展开结构。字段布局信息不证明字典键存在，也不能覆盖明确的未初始化状态。

## 3. 主要技术取舍

**保留名义类型，限制类型值的使用。** 类型由声明身份确定，字段相同或 NBT 编码相同不会使两个类型自动兼容。`type` 只能用于泛型参数，语言移除 `T!`。这减少了类型值与普通运行时值混用的情况。代价是程序不能把类型放进普通变量，也不能依靠字段相同获得隐式转换。

泛型支持声明处的 `out` 和 `in`，分别限制类型参数用于输出或输入位置。可变容器保持不变，可以防止不安全的元素写入。例如，Cat 继承 Animal，也不能自动将 `list<Cat>` 用作 `list<Animal>`，否则调用方可能写入其他 Animal。目前 `ImmutableList` 也保持不变。项目没有同时增加星投影或新的泛型推导规则。

**让 `as` 表示共享位置的视图。** `as` 不复制对象，不调用构造器，也不转换数值。普通复制则建立独立位置。这个选择使别名行为明确，也避免隐含的数据复制。代价是 `as` 不提供运行时类型检查，错误的重解释仍可能不安全。数值转换必须使用 `toInt` 等转换函数。

**采用保守的编译期分析。** 分支合并只保留所有可达路径共有的信息。未知调用或原始命令可能改变外部状态，因此编译器撤销可能失效的信息。纯调用可以保留信息。这个选择优先保证生成命令正确，代价是部分程序不能做更多常量优化。

**普通调用不按每组常量实参生成版本。** 普通参数保持声明的类型契约。需要特化的 readonly 泛型实参必须提供完整编译期值。这可以减少重复函数版本，并保持源码与导入库的调用规则一致。代价是编译器放弃部分针对单次普通调用的优化。

**保留必要的运行时存储成本。** 顺序求值、独立复制和递归调用可能需要保存快照或活跃值。统一存储层明确处理这些成本。它没有消除所有 NBT 调用帧，也不承诺每种高级语法都不生成额外命令。

**保留两种浮点后端。** 26.3 目标使用数值提供器和 FloatTag，旧目标使用四分量模拟布局。常量求值必须符合所选后端的精度和异常规则。未证明等价的旧浮点运算继续调用实际库函数。这样可以保留旧目标支持，代价是维护两套实现，且不能随意用宿主浮点运算替代目标运算。

**明确中断旧兼容路径。** 当前库格式为 MCFL77。旧格式和未知格式要求重新编译。旧语言写法及已有持久数据布局也不自动迁移。这个选择减少双套实现的维护成本，代价是旧项目需要修改代码或重建库。

`const` 只禁止再次赋值，不要求值在编译期已知。它也不禁止修改容器内容。需要限制内容修改时，应使用 readonly 约束。

## 4. 验证结果与边界

最终无过滤的 `cleanTest check` 实际退出 0。78 个测试套件共 617 项全部通过，失败、错误和跳过均为 0。测试覆盖统一值模型、语言限制、递归数据模板、原生接口、调用帧和新旧浮点后端。

标准库重建的语言错误和警告均为 0。三份 MCFL77 库资源的哈希一致。验证使用真实库往返和独立命令执行器，没有运行实际 Minecraft 服务端。

本次迁移没有加入 lambda、跨 tick 任务、异常系统或运行时类型反射。这些功能需要另行设计。

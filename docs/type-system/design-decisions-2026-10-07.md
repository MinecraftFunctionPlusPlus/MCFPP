# MCFPP 类型系统讨论决策记录

日期：2026-10-07。

范围：保存本轮讨论总结的第 1 至第 8 点及相应细节，覆盖设计目标、类型体系、方差、类型声明、object 配对、any、泛型约束和值/引用。lambda、跨 tick 和错误处理的完整方案继续讨论，不在本文定稿。

本文记录语言设计决策，不宣称编译器已实现。状态分为：**已确认**、**设计边界**和**待定**。既有实现或旧设计文档若与决策不同，需要后续迁移；本次未修改编译器。

## 1. 设计目标与平台边界

### 已确认

- 目标是高效、开发者友好、学习成本低，并符合 Minecraft 数据包能力。
- mcfunction 不提供可供 MCFPP 捕获、回溯和跨 tick 恢复的语言调用栈。
- 当前 NBT 模拟调用栈是临时实现，需要优化，不能成为新功能的统一前提。
- 跨 tick 的首要使用场景是全局定时任务与世界逻辑。
- 详细语义通过交互问答逐项讨论；未确认的建议不能作为最终决定。

### 设计边界

零成本抽象以相同语义、目标版本和生命周期保证下的合理手写命令为比较对象：不为未使用的能力承担统一运行时成本。保存必要快照、隔离独立实例、递归或重入所需的活跃数据仍有真实成本。

普通函数、引用、闭包或任务不应仅因使用高层语法就统一创建 NBT 包装对象或压入模拟栈。逻辑类型与物理布局分离，布局由实际使用决定。

### 待定

是否公开完整代数效果系统尚未确定。当前建议优先做好内部效果与控制流分析，不急于增加通用 perform/resume、多次恢复和通用运行时。

## 2. 保持名义类型体系

### 已确认

- 保留已有联合类型。
- 不引入全面结构式类型兼容；字段相同不自动建立普通声明类型之间的兼容关系。
- 不因为已有联合类型就立即补齐通用交叉类型 `A & B`。
- 现有 `as` 已能承担用户需要的一部分显式重解释用途，暂不再增加完整的结构式记录体系。

### 设计边界

`as` 与子类型证明分开。按现有规范，`as` 建立同一数据位置上的解释视图，不自动构造对象、补字段、复制载荷、转换数值或验证运行时类型。因此，可显式重解释为某类型，不代表满足该类型的泛型上界，也不证明方差转换安全。

交叉类型与结构式类型本身是不同概念。今后即使支持多个名义接口约束，也不要求开放任意类型位置的 `A & B`。

类型别名、显示名称、存储表示不应代替声明身份。同样采用 NBT 编码的不同语言类型，不因此自动变成同一种类型。

## 3. 泛型方差

### 已确认

采用声明处方差：

| 声明 | 含义 |
| --- | --- |
| `out T` | 协变 |
| `in T` | 逆变 |
| `T` | 默认不变 |

禁止 `*` 星投影。泛型参数的具体书写方式仍需与现有 `T as type` 声明语法整合；表中记法表达已确认的语义，而非已实现 grammar。

### 设计边界

假设 `Cat <: Animal`：协变允许 `Producer<Cat>` 向 `Producer<Animal>` 使用；逆变允许 `Consumer<Animal>` 向 `Consumer<Cat>` 使用；不变参数不提供这两种放宽。

编译器需要检查嵌套类型位置，而不是仅观察最外层参数或返回值。可读写成员通常使参数同时出现在输入与输出位置。返回可变容器也不能仅因为出现在返回位置，就被认定满足协变。

方差基于子类型关系，不直接沿用数值隐式转换。`int -> float` 的数值提升不能自动推广为 `Container<int> -> Container<float>`。

`T as type` 是类型参数；`i as int` 等是编译期值参数。后者不因为值具有相同整数类型就产生实例化之间的协变关系。

### 建议应用，尚需按 API 核对

| 类型/能力 | 建议 |
| --- | --- |
| 可读写容器 | 不变 |
| 可读写 `NBTRef<T>` | 不变 |
| 只提供值的接口 | 可考虑协变 |
| 只接收值的接口 | 可考虑逆变 |
| 函数类型 | 参数逆变、结果协变，并检查执行效果兼容性 |
| 若采用不可原地改写载荷的 `Result<T, E>` | 可考虑两个参数都协变 |

只读访问不代表深不可变，也不代表目标不会被其他引用或原始命令修改。

### 待定

具体标准库类型的方差、声明检查细节与使用处投影是否永不提供尚未定稿；当前不引入使用处投影。禁止 `*` 不自动意味着禁止泛型实参推导或默认实参，这两者需要独立决策。

## 4. 取消同名类型声明的泛型重载

### 已确认

同一命名空间中，不允许仅通过泛型参数数量或参数类型区分同名 data 声明：

```mcfpp
data A { ... }
data A<T as type> { ... } // 不可与上一个声明并存
```

`data A<i as int>` 与 `data A` 同样不能作为同名重载并存。

这不取消一个泛型声明的不同实例化：`A<int>` / `A<string>`，以及编译期值参数的 `A<1>` / `A<2>` 仍可具有各自身份。

同名 data 与 object 的伴随配对属于允许的独立规则，不是类型声明重载。

### 设计边界

声明名称先确定唯一参数列表，再进行实参绑定。不能在推导失败时改选另一个同名类型声明，也不能依靠未提供参数来表示另一种无参类型。

这项决定不自动禁止函数、工厂或构造函数重载；它们的规则单独处理。

当前主类型声明入口已有按名字检查重复的逻辑，作用域中也仍存在按参数类型列表查询泛型声明的数据结构。本文确定未来语义，不据此断言全部历史重载路径已经移除。

## 5. 独立 object 与伴随配对

### 已确认

object 可以独立声明，也可以与同名 data 配对。配对不改变 object 自己的泛型语义。

| 形式 | 含义 |
| --- | --- |
| 独立非泛型 object | 一份单例 |
| 独立泛型 object | 按编译期实参区分的单例族 |
| `data A<T>` 与非泛型 `object A` | 所有 data 实例化共享一份伴随对象 |
| `data A<T>` 与对应的泛型 `object A<T>` | 按对应实参配对伴随对象 |

同名的非泛型 object 与泛型 object 不能同时声明来形成对象重载；共享和按实参区分两种形式选择其一。

在当前语法中 object 模板使用 `object data`。例如：

```mcfpp
data A<T as type> { ... }

object data A<T as type> {
    private func test(value as T) -> T {
        return value;
    }
}
```

对应关系为 `data A<int> <-> object A<int>`。data 访问配对对象的私有 test 时，其返回类型对应当前 data 的 T。两个声明各自引入参数，通过配对绑定，不通过参数名字碰巧相同来绑定。

非泛型伴随对象没有可用的外层 T，私有权限也不会让未声明的 T 自动生效：

```mcfpp
object data A {
    private func test() -> T { ... } // 未声明 T，非法
}
```

但其中的方法可以引入自己的参数：

```mcfpp
object data A {
    private func test<U as type>(value as U) -> U {
        return value;
    }
}
```

data 中的 `A.test<T>(value)` 将该次调用的 U 绑定为 T。方法的独立参数不自动与调用者参数绑定；是否省略实参由后续推导规则决定。签名 `test<U>() -> U` 也不允许函数凭空构造任意 U。

### 设计边界

泛型特化生成多份代码，不应意外复制本应共享的非泛型 object 状态。反过来，泛型 object 的不同实参身份也不能因协变而合并。

私有访问权限、配对关系、类型参数绑定和对象状态身份分别建模，不能靠同名文本替代这些关系。

### 待定

泛型配对参数数量、顺序、种类、上界的精确匹配规则尚未定稿；当前建议一一对应，避免子集参数和隐式映射。对象成员的访问拼写、未限定私有调用的名字查找，以及初始化和 reload 生命周期需另定。

## 6. any 的明确擦除边界

### 已确认

允许 any 作为类型实参，例如 `list<any>`。当目标明确为 any 时，允许直接赋值和传参，不要求每次写 `as any`：

```mcfpp
var values as list<any> = [];
values.add(1);
values.add("hello");
values.add(someRef);
```

| 操作 | 规则 |
| --- | --- |
| 具体值赋给 any / 传给 any 参数 | 允许隐式擦除 |
| 向 list<any> 加入可存储值 | 允许 |
| 未知 any 自动还原为具体类型 | 不允许 |
| list<int> 自动变成 list<any> | 不允许 |
| 泛型推导失败时自动填入 any | 不允许 |

### any 与星投影的区别

- `any`：整个值的类型被擦除。
- `Box<any>`：已知是 Box，其实参明确为 any。
- `Box<*>`：已知是 Box，实参固定但未知；本语言不提供这种星投影。

可写 `Box<int>` 不能自动转为 `Box<any>`，否则另一方写入字符串会破坏原契约。要把一个整数列表变成独立的异构列表，需要显式创建并逐项转换/加入，不能悄悄改变共享可变容器的类型。

禁止星投影意味着部分异构泛型集合不再能直接表达。可通过泛型函数保留参数关系、通过明确的公共接口隐藏无关参数，或在必要边界使用 any；不把 Box<any> 当成星投影的替代品。

### 存储与操作边界

any 沿用擦除语义：编译器已知实际类型时可以使用有效的类型事实；未知时不能自动获得任意具体类型的操作。流事实不等于总有运行时类型标签。

隐式擦除不承诺所有后端操作都没有命令成本。容器写入可能需要把比分值编码到 NBT，仍需满足目标后端的载荷限制。擦除也不能让编译器专用值绕过普通值存储约束。

当前 TypeRelations 的目标 any 转换已有独立低优先级等级；本文确认语言方向，不宣称所有调用路径均已验证。

## 7. 泛型约束：待细化的方向

尚未最终确定约束语法及完整能力。当前建议优先支持名义子类型上界：

```text
T : Entity
T : Readable，同时 T : Writable
U : T
T : Comparable<T>
```

可以考虑 where 形式集中书写多个要求；不要求同时开放通用交叉类型表达式。

建议遵循以下边界：

- 上界限制合法实参；in/out 描述实例化之间的变化关系，两者不互相代替。
- 约束依据类型关系检查，不通过 as 或任意转换函数来满足。
- 泛型函数体按声明约束检查；具体调用碰巧具有额外成员，不应让未声明的要求自动成立。
- 特化负责优化，不应改变公共类型契约。
- 接口上界不自动提供 `T()` 构造能力，也不自动提供伴随对象的静态工厂能力。
- 需要构造实例时可先传入工厂函数，暂不急于加入特殊构造器约束。

未定项：默认上界、依赖约束范围、推导规则、默认实参、冲突/递归约束诊断、配对两侧约束的一致性，以及与现有编译期值参数的整合。

## 8. 普通值、引用描述与引用目标

### 已表达的偏好

倾向分别提供 ScoreRef 与 NBTRef<T>，避免一个含义宽泛的 `ref var` 同时涵盖不同寻址与操作模型。

ScoreRef 的逻辑描述示例：

```snbt
{obj: "xx", holder: "xx"}
```

NBTRef 的逻辑描述示例：

```snbt
{nbt: "storage", source: "test:test", path: "xxx.xxx"}
```

### 设计边界

必须区分普通值、引用描述本身、引用指向的目标。复制引用描述仍指向同一目标；读取目标得到值；写入目标改变共享位置。引用描述采用 NBT，不意味着每次使用必须实际创建一个新的描述对象，静态已知地址可以直接用于命令生成。

可读写 `NBTRef<T>` 应保持不变性。即便 Full 数据可被只读地看作 NameOnly，也不能让 `NBTRef<Full>` 自动变成可整体写入的 `NBTRef<NameOnly>`，否则替换目标可能删除 Full 所需字段。

引用身份和目标状态不同：不可重赋的引用变量不等于不可变目标，只读访问也不保证其他别名不会修改目标。

### 待定

- 是否最终采用 `.get()` / `.set()` 显式读写。
- 普通 NBT 值、对象值和引用值的复制深度与成本。
- 引用字段是否可修改，以及构造/验证入口。
- 失效引用、缺失目标、目标类型不匹配的处理方式。
- 临时位置与持久位置的区分、跨 tick 生命周期。
- 只读引用/接口的具体表达与方差。

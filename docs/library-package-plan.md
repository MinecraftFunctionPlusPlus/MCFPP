# MCFPP 预编译库、导入导出与 Mcfpm 接入计划

日期：2026-10-29。状态：待用户审查；批准后才建立可执行任务图并实施。

## 1. 已确认的目标

用户通过 Mcfpm 安装已经发布的 MCFPP 库，随后编译项目即可使用库中的声明和资源，无需取得库源码或运行作者的构建流程。库保存可分析的函数体；调用方提供编译器已知实参时，仍能执行现有的常量传播、分支简化、实例化及其他适用优化。

兼容承诺从第一版正式发布的库格式开始：新版编译器读取旧版库；旧版编译器拒绝更新的库格式，给出清楚的升级诊断。当前未发布的开发缓存（目前 LibBinFormat.VERSION = 87）可以直接调整，由作者重新导出。

## 2. 本稿提议的技术方案

### 2.1 预编译的边界与现场优化

- 库的主体包含声明、类型、常量、词法环境、依赖符号引用以及可继续分析的语义语法树。普通函数也保留现场优化所需的函数体。
- 泛型、只读参数、lambda / 回调、默认参数及字段初始化表达式保留参数化结构和正确的声明绑定环境。
- 生成的 Minecraft 函数、静态数据包资源和运行时支持文件可以随库携带；编译器决定直接链接、复用或根据实参生成对应实现，并保证同一资源只有一个有效输出来源。
- 沿用当前语言的优化与副作用语义：未知值继续走运行时路径；已知值不能导致参数副作用被删除、重复求值，或丢失别名、引用、上下文借用事实。

### 2.2 发布格式 v1

采用独立于编译器内部类的显式二进制协议。v1 在规范中固定段标识、节点/类型标识、字段编码和引用规则；使用有长度边界的数据段，避免依赖 Kotlin/JVM 类名、字段反射、enum ordinal 和 ANTLR token 编号。

逻辑结构如下（名称属于本稿建议，可在不改变语义的情况下调整）：

| 部分 | 保存内容 |
|---|---|
| Header | magic、单调递增的库格式版本、语言语义/运行时 ABI 标识、必要的目标信息 |
| Symbols / Types | 声明与类型表、公开可见性、稳定的跨包引用和库内编号 |
| Bodies | 独立的语义语法树、参数化实现、默认表达式与初始化器 |
| Runtime / Resources | 预生成函数的关联、静态资源和装载映射 |
| Debug | 可选的相对源文件位置、文档及源码映射 |

库格式与编译器发行版本分别管理。普通优化器修复不必升级库格式；持久化结构或既有操作语义发生不兼容变化时才升级。新版通过对应历史解码器把旧发布格式转换为当前内部表示，并保留旧操作的含义。writer 默认生成当前正式格式，本次不增加导出任意历史目标格式的功能。

语义语法树必须覆盖当前能够进入库的表达式、语句及声明相关结构。当前 TypedIR 只覆盖部分编译路径，不能直接把它整体序列化作为完整替代。实现中为源文件和库函数提供通向现有语义分析、优化和生成逻辑的共同桥接；ANTLR 上下文仅作为编译会话内的解析实现，不进入发布协议。不得用重新解析保存的源码来代替持久化语义树。

### 2.3 符号身份、可见性和依赖

- 公开声明以包身份、声明路径和必要签名区分；包版本由 Mcfpm 已解析图提供。包坐标与语言命名空间保持各自含义。
- 泛型参数通过所属声明和参数序号定位。私有/局部声明使用库内编号，读取时映射为当前会话身份，避免原样恢复进程内 Opaque 递增值。
- 保留私有实现和必要类型以支持库内调用及现场优化，对使用者的访问继续执行现有访问控制。
- 跨库引用指向依赖声明，不依赖重复保存其他包的内部对象图。新编译器能够在全部库注册后统一解析这些引用。
- 本次沿用当前 import 和访问语义；新增转导出语法、强制限制应用访问传递依赖等语言策略留待另行讨论。

### 2.4 导入、导出与资源

- 引入明确的导出会话和导入会话，提供面向流/归档资源的正式接口；库身份、兼容信息和诊断随接口传递。
- 导入按“解码与校验 → 注册全部声明 → 统一绑定跨库引用及声明环境 → 编译消费方”执行。错误不能伪装成成功返回，失败不留下可继续使用的部分导入状态。
- 修复同一命名空间合并时枚举、类型别名遗漏的问题，统一声明冲突的诊断及来源信息。
- 覆盖普通函数、泛型、data / object / 继承、枚举、别名、属性与运算符、lambda、默认参数、初始化器、MNI/宏描述和引用 helper 等当前已支持的库内容。
- 导出只登记本库拥有的声明、标签贡献和资源，跨库需求通过引用/依赖表达；避免把累计全局状态当成本包所有内容。
- 输出按规范排序，使用字符串/类型/声明引用表复用内容；发布字节不依赖绝对路径或会话计数器。先写临时产物，成功后替换，保护已有有效库。
- 保留当前本地目录、ZIP/JAR 和内置标准库的使用入口，内部统一接入新装载接口；历史未发布二进制需重新生成。归档目录差异在适配层规范化。

### 2.5 Mcfpm 接入

涉及仓库：当前 MCFPP 工作区，以及 GitHub 上的 Alumopper/Mcfpm。批准后定位/准备 Mcfpm 工作副本，保留两个仓库现有未提交修改。

- Mcfpm 继续负责坐标、依赖解析、锁文件、仓库、下载、缓存和载荷校验；MCFPP 负责语言语义和代码生成。
- mcfpm.toml 是包依赖声明来源，mcfpm.lock 固定完整解析结果；mcfpp.json 保存编译目标、源目录和输出等编译设置。
- 目标使用流程：作者导出库 → 使用现有 Mcfpm pack / 发布能力生成包 → 使用者执行 mcfpm install → 执行 mcfpp mcfpp.json 消费已锁定并下载的库。编译本身不更新锁文件或重新选择依赖版本。
- 正式库载荷继续使用 compiler.mcfpp.library。外层沿用 Mcfpm ZIP 载荷模型，内部包含新 bin.mclib、模块资源描述和必要资源；在规范中统一根路径。
- 更新 mcfpp-adapter，使用正式接口替换旧配置读取 ABI 和 READ_LIB 结束 hook 的注入方式。保留按依赖顺序注册、统一解析以及编译会话结束时清理的行为。
- 配对资源包和既有数据包载荷沿用 Mcfpm 模型。MNI / JVM 插件沿用现有信任与加载流程，接入实际 MCFPP 公共 API，保证共享类型身份和可用性。
- 保留本地 includes / jars 开发入口；发布时通过已有迁移校验要求把需要分发的内容表达为 Mcfpm 依赖或载荷。

## 3. 建议的交付顺序与任务边界

下表是待批准的实施分解；本次只发布提案，不创建可执行任务图。批准后，按实际文件所有权把各批次细分为有明确交付物的叶任务，测试随功能完成，不以整批作为一个巨型叶任务。

| 批次 | 可审查的交付物 | 主要依赖 |
|---|---|---|
| A. 格式与接口契约 | v1 格式、语法树节点范围、身份/资源/兼容规则；导入导出和 adapter 的接口契约 | 本计划批准 |
| B1. 容器与声明 | Header / 分段编码、声明/类型/常量表、身份映射及兼容诊断 | A |
| B2. 函数体表达 | 表达式/语句持久化树与现有分析入口的桥接；先闭合一个普通函数的导出—调用链 | A；集成时使用 B1 |
| C1. 基础库可用 | 普通调用、已知值与未知值、默认参数、控制流、副作用的源码/库一致性 | B1、B2 |
| C2. 复合声明可用 | data / object / 继承、属性/运算符、枚举/别名、初始化器及跨库类型绑定 | B1、相关 B2 接口 |
| C3. 参数化与编译期能力可用 | 泛型/只读参数、lambda/回调、MNI/宏、引用 helper 的导入和现场实例化 | B1、相关 B2 接口；按具体能力细分真实依赖 |
| D1. 完整导出与标准库 | 导入会话、命名空间合并修复、资源归属、确定性/完整写入；标准库与本地入口迁移 | B1、B2；各能力完成后集成 |
| D2. Mcfpm 闭环 | adapter、锁图消费、配对资源与 JVM 载荷接入；本地仓库安装后实际编译 | A 接口可先对接，实际联调依赖 C1/D1 |
| E. 发布就绪 | 当前能力覆盖检查、冻结 v1 历史样本、教程与示例、两仓库集成验收 | C1–C3、D1、D2 |

A 完成后，协议编码、语法树实现和 Mcfpm 接口适配可在不冲突的路径推进。实际共享的 Function、Project、分析入口等文件按明确所有权串行合入；统一安排 Gradle 构建，避免多个构建者写同一输出目录。

执行遵循工作流技能：Astra 协调，原生 gpt-6.1-sol 承担适合委派的实现；必要的小修复可直接处理。宿主共四个并发槽，实施时按实际空闲槽和写入冲突调度。重要文件格式/导出变更由非作者复核已有结果。

## 4. 验收要求

1. 实际闭环：在干净消费项目中仅通过 Mcfpm 安装库，再运行 MCFPP 完成编译，输出可执行的数据包；消费者不需要库源码，库私有实现和必要运行时资源齐全。
2. 现场优化：相同示例直接由源码编译和经导出库编译，运行结果一致；使用已知/未知/混合实参核对当前适用优化，关键命令形状与副作用次数符合既有语义。覆盖依赖已知值的泛型、回调和默认表达式。
3. 重要库能力：重用现有库、继承、lambda、MNI、entity/ref 等检查；确认这些能力经过新格式后仍可调用，访问控制、别名、上下文借用及多库词法环境正确。
4. 多库组合：两个独立构建的库共同导入时身份不会碰撞；同一命名空间的枚举和别名都可见；依赖符号能统一绑定；资源和初始化贡献不会重复输出。
5. 兼容协议：冻结正式 v1 字节样本，后续读取测试使用固定样本；未来版本头被旧读取器明确拒绝。首版建立长期夹具，不把尚不存在的未来编译器结果报告为已验证。
6. 完整与可复现：相同输入和设置、不同工作目录/新编译会话产生相同库字节；中断/失败导出保留原有效产物；截断、未知版本等常见损坏得到可定位诊断。
7. 标准库和 Mcfpm：新格式标准库重新生成并可使用；本地 Maven 仓库覆盖发布物生成、安装、缓存/锁图消费和编译，包含资源及 MNI 的必要场景。
8. 交付文档：说明发布内容、调用点优化、版本规则、包坐标与命名空间关系、本地开发及安装/导出步骤，并提供可运行的作者/消费者示例。

## 5. 验证方式与当前证据

本计划基于当前未提交工作区的源码检查，以及通过 gh 读取的 Mcfpm main 接口；之前没有为本计划执行新的产品测试或性能测量。现有测试代码表明目前依赖 AST 现场编译，并明确拒绝旧缓存格式；这些是设计依据，不等同于新格式的通过证据。

实施时先运行相关定向检查；通过后只因相关修改、失败或具体证据缺口补验。涉及编译器多个主路径，最终代码冻结时安排一次 MCFPP 全量回归和 Mcfpm 相关模块/集成检查。复用适用于实际工作区的历史证据，保持文件格式变更所需的独立复核。

体积与速度优化以实际数据为依据，首版不设未经用户要求的压缩率、性能阈值或压力规模。字符串表/类型表和去除解析器对象图属于格式设计；按需加载和进一步缓存优化只有出现实际需要时再评估。

## 6. 审查重点与范围边界

- 已确认：预编译分发；保存语法树以支持现场优化；新版读旧、旧版拒新；未发布开发缓存无需兼容。
- 随本稿审查：独立的持久化语义语法树与显式二进制协议、符号身份方案、完整库能力迁移、Mcfpm 消费入口和上述交付/验收范围。
- 本次交付使用现有语言语义与包管理基础。新 import/export 语法、多版本同包共存、通用优化器重写、LSP 全面迁移，以及公共仓库部署/真实发版，分别需要独立范围决定。
- 当前主要实现难点是各 ANTLR 消费路径到持久化树的桥接。若探索发现需要改变本稿保证的语言能力、兼容方向或两仓库协议，先提交具体差异供审查；常规接口命名和代码组织由实现自行决定。

审查通过后，按批准的确切提案修订建立任务图并开始实施。浏览器中的编辑或评论会产生新修订，执行以用户批准的最新正文为准。

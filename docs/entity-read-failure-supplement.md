# 实体字段读取失败合同：已批准补充方案

关联：已批准的实体与上下文计划 §3、§7.4。用户于 2026-10-23 通过本聊天明确选择“采用 tryRead 同步回调方案”。以下为已批准合同，实际交付状态随实体集成任务记录。

## 已确认的现状

实体属性等命令已有 `CommandResult { result: int, success: bool }`。`NativeMinecraftCommandOperations.captureCommandResult` 每次初始化独立结果并写入成功标志，可直接复用。

实体 NBT 字段和现有分数位置的裸值读取没有等价合同：例如 `StorageAccess.loadScore` 直接读取并发布数值，没有向调用者返回本次读取是否成功。不能将这一行为当作已满足获批计划的失败处理要求。

## 已批准的补充

为实体 NBT 字段及实体分数位置增加同步 `tryRead` 读取入口，复用现有 lambda 和 bool；它只在一次实际读取成功后调用正文，并返回本次是否成功：

```mcfpp
var found = target.dat.air.tryRead { air ->
    // air 是本次成功读取的普通 short 值，可按普通值规则复制和传递。
    // 此回调继承调用点的 Minecraft 上下文。
}
if (!found) {
    // 没有目标、字段或分数时在这里处理。
}
```

- 接收端是读取地址，不能先隐式加载裸值再调用 `tryRead`。
- 每次调用清理结果临时槽，执行一次读取；不存在的目标/字段/分数返回 false 且不进入回调。已经存在且数值为零的字段仍返回 true。
- 回调签名为 `(字段类型) -> void`，同步执行，局部 return 沿用普通 lambda 合同。它不创建新的实体执行上下文。
- 成功的值作为普通值快照传入；上下文借用句柄仍遵守原有生命周期限制。
- 直接实体数据写入继续使用现有地址接口；没有显式失败处理的实体裸值读取给出诊断，提示改用 tryRead。不能因处于 withEntityCtx 内就假定所有字段或分数必定存在。
- 已返回 CommandResult 的属性/经验查询复用原合同。该补充不实现通用 Result、可空类型或异常系统。

## 未采用的替代方案

审阅时也提供了专用 `EntityReadResult<T>` 返回对象的选项。用户选择了上面的同步回调方案，本次不实施该替代接口。

## 对应验证

成功读取非零值和零值、同一读取点先成功后失败、不存在实体/字段/分数、失败回调不执行、回调执行者与空间保持调用点上下文。沿用当前解释器/DSB，不运行实际游戏。
